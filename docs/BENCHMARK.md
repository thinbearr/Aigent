# Benchmark: what was run and what it says

Everything below is regenerated by one command (about 10 seconds when the cases already exist via `--cases results/cases`; about 4 minutes when it also regenerates all 160 cases):

```bash
cyberarena bench --out results --seeds 1 2 3 4 5 --systems A C D --hai external/hai-21.03
```

Outputs: `results/tables.md`, `failures.md`, `cases.csv/json`, four figures, `hai.md`, `run_info.json` (versions, seeds, file hashes).
The run recorded here: Python 3.12.10, Windows 11, 2026-11-09. Scenario/model hashes: `paper/scenario_freeze.txt`.

## Protocol

* Range: the simulated Kaveri plant. For every (family, seed) the range is reset, background activity is seeded, the family runs through the plant's real entry
  points, and the evidence is exported to `events.jsonl` + `tickets.csv`; ground truth goes to a separate `truth.json` that only the scorer reads.
* The engine reads those files through the same adapters a real deployment uses (not through the simulator's internals).
* 32 families (16 attack, 16 benign; 16 of them hard) x 5 seeds = 160 cases. Positive class = attack. One alert window per case (the whole case).
* Statistics: 95 % Wilson intervals; exact McNemar on paired correctness, Holm-adjusted; pooled per case and at family level (majority over seeds).

## What was NOT run (important)

* **Systems B (single LLM) and E (single LLM with the same records) were not run in the final results.** A first full run that included them was abandoned
  (see `paper/scenario_freeze.txt`, addendum 2). The code for B and E exists and works with a local Ollama model (`OLLAMA_MODEL=llama3.2:3b`, ~10-15 s per call on
  this laptop's CPU); a 3B model is a weak baseline, so a cloud or larger local model is needed for the comparison that matters. **So there is currently no data on
  agents vs a single LLM given the same records.** Earlier exploratory runs (CyberArena-Final, different scenarios) showed a tie; do not claim otherwise without new data.
* No live-plant data. OpenPLC / Docker: untested.

## Results (160 cases, from `results/tables.md`)

| System | Accuracy (95% CI) | Recall | False-alarm rate | Precision |
|---|---|---|---|---|
| A rule-based detector | 66 % (58-73) | 100 % (95-100) | 69 % (58-78) | 59 % |
| C agents, no Critic | 78 % (71-84) | 94 % (86-97) | 38 % (28-48) | 71 % |
| D agents + Critic | 96 % (91-98) | 99 % (93-100) | 8 % (3-15) | 93 % |

Hard cases only (80 cases): A 44 %, C 56 %, D 91 % accuracy. Easy cases: C and D both 100 %, A 88 %.

Cost per alert (deterministic code, CPU): A 0 tool calls; C 5.3; D 7.3; about 1 ms each; no LLM calls or tokens.

Ablation (Critic checks switched off one at a time, D = full):

| C (no Critic) | 78 % | 94 % | 38 % |

## Reading it honestly

* The pooled test treats the 5 seeds of a family as independent; they are not. At family level D vs C is **not** significant after Holm correction. Do not lead with the pooled p.
* **The seeds barely vary the outcome** (per-seed accuracy 97/97/97/94/94 % for D, identical for A and C). Seeds change values and noise, not the story. More seeds do not add much; more
  *structurally different* scenarios would.
* The maintenance-window check carries most of the Critic's value. The change-scope check changes little overall (p = 1.0) although it matters for the "beyond the approved value" families.
* Because the authors wrote the scenarios and tuned the weights on a related earlier set, these numbers show the *mechanism*, not generalisation.

## Where it fails (from `results/failures.md`; not tuned away)

| case | system | why |
|---|---|---|
| **B07 second ticket is the valid one** (0/5 for D) | D | **Engine defect**: `TicketStore.covering()` returns the first ticket covering the asset and time, not the one assigned to the acting user, so the engineer's own ticket is reported as "belongs to someone else". |
| **B01 approved setpoint change** (1/5 wrong for D) | D | **Engine defect**: the change-scope check compares *every* config event on the asset, including routine operator nudges by another user, with the ticket's limit, so a bystander's write can "exceed" the ticket. |
| **A15 blocked logic download** (0/5 C, 1/5 wrong D) | C, D | A refused attempt is weak evidence (confidence 0.57-0.59, just below the 0.6 threshold). A policy question: should a blocked attempt be an incident? |
| Rule detector: 55/160 wrong | A | Every ticketed change looks like an attack to a rule with no context (11 benign families false-alarm 5/5). This is the point of the Critic, not a flaw to fix. |
| Agents without Critic: false alarms on B01, B03, B06, B07, B12, B15 | C | Approved changes are flagged because nothing checks tickets. |

## HAI (process anomaly only; does not test the Critic)

`results/hai.md`: one file (`hai-21.03/test1.csv.gz`, 6,149,549 bytes, sha256 `532de41b...`). A z-score baseline fitted on the first 2,000 s detects all 5 attack segments, but
point precision is 1-2 % (about 0.5 false-alarm episodes per hour): benign operating-point changes after the short baseline are flagged. A first run used quantile thresholds that
saturated (identical rows), so the threshold grid was changed to multiples of the maximum baseline score before the numbers above were recorded; both runs are mentioned here on purpose.
No ticket overlay was used. HAI cannot validate the Critic.
